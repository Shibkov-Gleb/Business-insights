# Изменения в проекте

Хакатон разрабатывается в `hackathon/alfa-2026`; `main` и теги личного продукта сохраняются. [Требования](docs/hackathon-requirements.md), [матрица](docs/hackathon-compliance.md) и [состояние приёмки](docs/hackathon-acceptance.md) — отправная точка изменения.

## Рабочий процесс

1. Проверьте `git status` и используемую ветку. Сохраняйте чужие незакоммиченные изменения. Для параллельной работы используйте отдельную ветку/worktree, а не два checkout одной ветки.
2. Воспроизведите проблему на синтетических данных; не добавляйте исходные CSV/PDF, `.env`, cookie или журналы с закрытым контекстом в Git.
3. Изменяйте общие DTO в `packages/contracts`, права — на API и worker одновременно. При изменении контракта обновите OpenAPI: `pnpm exec tsx scripts/hackathon-openapi.ts`.
4. Добавьте целевую проверку для изменённого поведения. Для документации достаточно `pnpm docs:check` и визуальной проверки; платные тесты не являются частью обычного запуска.
5. Обновите соответствующий раздел документации и `docs/implementation-status.md`. Коммит должен описывать итоговое изменение.

## Проверки

```sh
pnpm docs:check
pnpm typecheck
pnpm lint
pnpm test
```

Integration/E2E и сборка нужны при изменениях, затрагивающих соответствующее поведение; команды в [приёмке](docs/hackathon-acceptance.md#reproduce). Live требует явной конфигурации и подтверждённого запуска. Не меняйте метки оценочного набора ради улучшения показателя; сохраняйте исходные неудачи и отличайте независимую оценку от регрессии.

## Перед передачей жюри

Следуйте [комплекту сдачи](docs/hackathon-release.md). Не создавайте `alfa-hackathon-v1`, пока открытые проверки не завершены; идентифицируйте кандидата через `git rev-parse HEAD`. Скриншоты должны показывать настоящие экраны и дату съёмки; demo-метрики не выдаются за живую оценку.

## Место контроля в архитектуре

Браузер не обращается к БД или LLM напрямую. API проверяет session → Origin/CSRF → membership/company grant → DTO/version/idempotency. Worker повторно проверяет доступ до/во время инструмента и при транзакционной публикации. SSE проходит тот же authorized-job контроль. Банковский корпус доступен только аутентифицированному участнику с разрешённой компанией; административный импорт дополнительно требует owner/admin-доступа.

Клиентские данные остаются в закрытых БД/files/checkpoints. Корпус кейса общий для разрешённых участников; это не пользовательский межорганизационный документный архив. При расширении на частные банковские корпуса потребуется отдельная tenant-привязка материалов.

## Инструменты и журналирование

Trace содержит request/run ID, стадию, tool, длительность, использованные признаки/источники/версии, usage и код ошибки. Сырые ключи и тексты документов не выводятся в общий лог; закрытые основания доступны через авторизованные API. Внутренние рассуждения LLM не сохраняются.

Инструменты только читают источники, анализируют и сохраняют результат в приложении. Автономных банковских операций, рассылок, CRM-действий и рекламы нет. Безопасность grounded-output снижает риск, но не доказывает смысловую корректность: валидная цитата может быть неверно истолкована. [Оставшиеся проверки](hackathon-release.md).
